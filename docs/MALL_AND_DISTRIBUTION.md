# 商城与游戏分发

> 覆盖**兑换商城**、**心愿商城**、**游戏解锁与下载分发**三块。
> 领域口径来自 `kid-quest-farm-2d` 的 `docs/wish-mall-spec.md` 与 `src/domain/redeem.ts`。
>
> ⚠️ **2026-10-29 已按上游 v3 口径更新**：心愿商城从「只收券」改成
> **券 + 积分混付**（与兑换一字不差）。v2 的那条**已作废**。

---

## 1. 两个商城的区别（设计的地基）

系统里有**两个**商城，很容易混。它们的分工是刻意的：

| | 兑换商城 | 心愿商城 |
|---|---|---|
| 收什么币 | **兑换券优先 + 积分补差** | **同样是混付**（v3 起） |
| 混付 | 允许（1 券 ≡ 1 分） | **允许，同一套规则** |
| 谁定价 | 家长 | 家长（**逐个商品**开放） |
| 成交在哪 | App 内标记「已给过」 | **App 外**（淘宝），家长去买 |
| 典型商品 | 零食、看 30 分钟平板 | 泡泡玛特、学习机、游戏盲盒 |
| 接口前缀 | `/api/redeem/*` | `/api/wish/*` |

### 1.1 为什么 v3 把心愿商城的「只收券」废掉了

**v2 的做法**（2026-10-28，第一版）：心愿商城只收兑换券，理由是
「混付会让『积分能不能换实物』变成一个是非题，而它应该是不能」。

**v3 的改动**（2026-10-29，家长拍板）：

> 「就跟兑换模块一样的，可以用兑换券和积分兑换」
> 「兑换 里的东西都是一样，都能用兑换券或者积分，包括游戏也一样。
>   不需要去心愿商城换。心愿商城只是标明心愿的。」

**代价是明知的**：「积分也能买 ¥69 的盲盒」这件事**部分成立**了 ——
家长接受，因为不这样的话，一个积分很多、券很少的孩子在心愿商城里
什么都换不了。

**分账仍然券优先**：券够的时候一分积分都不动（有单测钉着）。

### 1.2 分账规则（纯函数，**只有一处实现**）

```go
entities.PlanRedeemPayment(price, couponBalance, pointsBalance)
```

```
1. 兑换券和积分 1:1 等价
2. 先花兑换券，花光了再用积分
3. 一件东西可以两种币混着付
```

⚠️ **心愿商城不要再写一遍分账公式**，直接委托这一个函数。

两处各写一遍的话，改一处忘另一处时**界面预览和真正扣款会算出两个数**，
差额通常只有几分 —— 孩子的余额看起来就是「莫名其妙少了 1」。

**为什么「券优先」不是技术选择**：券是农场产出的出口，
先花券能让孩子感受到「种地有回报」。这个顺序写死在纯函数里，
UI 预览和真正扣款用的是**同一份** —— 预览说「30 券 + 20 分」，
扣款就必须是同一个数。

实测：

```
余额：100 券 + 150 分
兑换 30 分的东西 → 扣 30 券、0 分   ✓
```

## 2. 兑换商城

### 2.1 商品（家长创建）

`POST /api/redeem/item/create` 🔒

```json
{
  "name": "周末玩平板30分钟",
  "emoji": "📱",
  "category": "screen",
  "cost": 50,
  "note": "周末才能用",
  "limit_per_day": 1,
  "once": false,
  "stock": -1
}
```

| 字段 | 说明 |
|---|---|
| `cost` | 所需**「分」**（1 券 = 1 分）。不是「积分」，是中性计价单位 |
| `limit_per_day` | 每天最多换几个（**每天重置**），0 = 不限 |
| `once` | 一次性（**永不重置**）。换过就不再出现 |
| `stock` | 库存，`-1` = 无限 |

> ⚠️ `once` 和 `limit_per_day` **不是一回事**：那个每天重置，这个永不重置。
> 判据是**兑换记录**，不是库存 —— 库存是家长手填的，记录才是事实。

分类：`snack` / `gift` / `screen` / `outing` / `privilege` / `custom`

### 2.2 列表（孩子端）

`POST /api/redeem/list` 🔒

每个商品附带：
- `plan`：按当前余额算好的分账预览（券多少 + 积分多少）
- `can_redeem`：现在能不能换
- `remaining_today`：今天还能换几个（`-1` = 不限）
- `blocked_by_limit`：是否被每日限额挡住

**过滤**：已归档、`once` 换过的、库存为 0 的都不返回。

### 2.3 兑换

`POST /api/redeem/redeem` 🔒

```json
{ "item_id": "R1793257629124790", "quantity": 1, "client_request_id": "uuid" }
```

**响应**

```json
{
  "code": 200,
  "data": {
    "record_id": "RR1793257629219574",
    "name": "一份小饼干",
    "plan": { "harvest_paid": 30, "points_paid": 0, "total": 30, "affordable": true },
    "description": "30 兑换券",
    "wallet": { "points": 150, "coupon": 70, "diamond": 0 }
  }
}
```

**事务边界**（全部原子）：

```
1. 加锁读商品（防并发改价 / 改库存）
2. 校验 once / 每日限额 / 库存
3. 算分账（券优先）
4. 扣兑换券 + 扣积分
5. 写兑换记录（含余额快照）
```

### 2.4 兑现与取消

| 接口 | 作用 |
|---|---|
| `POST /api/redeem/fulfill` | 家长标记「已经给过了」 |
| `POST /api/redeem/cancel` | 取消并**退券退分** |

**防重复退款**：必须在**事务内 CAS 更新**，不能靠按钮 disabled ——
两个标签页同时点会各退一次。退款按记录里的分账退
（`CouponPaid` / `PointsPaid`），**不重新读商品价格**：商品改价了也不能退错。

实测：

```
兑换 30 券 → 余额 70
取消       → 余额退回 100   ✓
再取消     → 10060701「这笔兑换已经处理过了」  ✓
```

## 3. 心愿商城

### 3.1 状态机

```
（商品层）locked ──家长定价──▶ open
                                  │
（订单层）wished ──孩子确定兑换──▶ committed ──家长确认──▶ confirmed ──▶ done
   ▲                                  │
   └────────── 取消（退券）─────────────┴──▶ cancelled
```

| 状态 | 谁推进 | 券 | 说明 |
|---|---|---|---|
| 商品 `locked` | — | — | 家长还没开放。孩子只能「想要这个」 |
| 商品 `open` | 家长 | — | 已定价，孩子可以换 |
| `wished` | 孩子 | 不动 | 只是意向，随时可撤 |
| `committed` | 孩子 | **扣掉** | 已兑换，等家长确认 |
| `confirmed` | 家长 | 不动 | 家长已去外链购买 |
| `done` | 家长 | 不动 | 买好了 / 收到了 |
| `cancelled` | 家长 | **退回** | 买不成、不想要了 |

> **商品层的 `open` 是本家庭的设置，不是商品的全局属性** ——
> 所以 `voucher_price` 存在 `WishOffer` 表（按 `uid + item_id`），
> 不写进 `WishItem` 目录。

### 3.2 为什么钱必须真扣

**因为成交在 App 外面。** 钱如果不扣，孩子可以同时挂 10 个「已兑换」，
家长每个都要去淘宝买 —— 那是灾难。

### 3.2.1 扣的是**两种币**，退款也必须退两种

2026-10-29 起混付，所以一次成交可能同时扣券和积分：

```
孩子确定兑换： 券   delta = -voucherPaid,  source = 'wish_redeem'（兑换券账本）
              积分 delta = -pointsPaid,   source = 'wish_redeem'（积分账本）
家长取消：     券   delta = +vouchersHeld, source = 'wish_refund'
              积分 delta = +pointsHeld,   source = 'wish_refund'
```

两条硬规矩：

1. **为 0 的那一侧不写账** —— 写一笔 delta 0 的流水，界面里会凭空多出
   一条「心愿商城 0 券」。
2. **订单上同时记 `vouchers_held` / `points_held`，退款按这两个数原样退** ——
   只退一种的话，另一半**凭空蒸发**，而且**不报错**
   （账本只看 delta 之和，症状只会表现为「孩子的钱少了」）。

### 3.3 数字商品和实物共用状态，但文案必须分叉

| | 交付时点 | `committed` 的意思 | 界面上该说 |
|---|---|---|---|
| 盲盒 / 盒子 | 兑换当场 | 东西**已经给了** | 「已经放进你的游戏柜了」 |
| 玩具 / 学习 / 收藏 | 家长买完点确认 | 等家长去外链买 | 「等爸妈确认」 |

**判据是 `opened_game_id != ""`，不是 `kind`** ——
盒子装包失败会走取消退回，那种单子本来就不该显示成「已交付」。
服务端在 `WishOrderView.digital` 里算好给前端。

### 3.4 盲盒

```go
entities.BlindBoxRemaining(pool, owned)  // 池子减去已拥有 + 去重
entities.PickBlindBox(pool, owned, rand) // 开奖；池子空返回 ""
```

**三条硬约束**：

1. **先算池子再扣钱** —— 池子空了要直接拒绝（`10070701`），
   不能先扣再发现没得开。
2. **去重** —— 池子里同一个 id 写两次会让那一款概率翻倍，
   而这种错误在代码里看不出来，只有概率分布变了。
3. **用 `crypto/rand`** —— 不能用时间戳种子。
   盲盒必须**不可预测**，否则孩子（或任何读代码的人）能算出下一次开出什么，
   「盲盒」就变成了「选盒」。

### 3.5 兑换 = 撤销交易，所以游戏要一起收回

```
孩子兑换 → 扣 10 券 + 20 分 + 授予游戏
家长取消 → 退 10 券 + 20 分 + 收回游戏
```

不收回就是「白拿」：兑换 → 立刻取消 → 钱退回来了、游戏还留着。
那就是印钞机。

**实测**：

```
兑换盲盒 → 券 100→80，开出 prizepark，游戏数 1→2
取消     → 券 80→100，游戏数 2→1   ✓
```

> ⚠️ `RevokeGameWithTx` **只删 `user_game` 那一行，不删存档**（`game_kv`）。
> 取消往往是家长「这次先不换」，过几天可能又给买了 ——
> 存档里有孩子辛苦攒的进度（农场等级、金币），删掉等于惩罚孩子。

### 3.6 「已经换到的游戏」必须有一份卸载不掉的记录

游戏类商品的交付 = 装包，而「拥有」一直是从已安装列表派生的。
但**卸载会把包和存档一起删掉** —— 删完之后这个游戏
既不在已安装列表、也不在钻石账本（心愿商城不走钻石账本），
于是心愿商城认为「孩子没买过」：

- 盒子卡片变回可兑换 → **再扣一次券**
- 盲盒池子把它放回去 → **再开出来一次**

券是真金白银攒的，卸载一次就白扣一次，而且全程不报错。

所以服务端从 `wish_order` 反推「兑换到手过」的游戏
（`ListRedeemedGameIDs`），和 `user_game`、默认拥有**三个来源一起**算进 `owned`。

### 3.7 家长待办：`wished` 也算，但**判据不是 `status`**

改动之前只收 `committed` / `confirmed`（孩子**已经花掉钱**的单子）。
于是孩子点完「🤍 想要这个」、他那一侧写着「已经告诉爸妈，等他们定价」，
家长那一侧却**一片安静**。

`POST /api/wish/pending` 返回两个**分开**的计数：

| 状态 | 计数 | 家长要做的 |
|---|---|---|
| `wished`（**还没定价**） | `wished_count` | 定价，或者这次先不换 |
| `committed` / `confirmed` | `action_count` | 去外链买，或者收尾 |

合成一个的话，文案只能写成「有 N 单等你处理」，等于什么都没说。

#### ★ 判据取「这件商品有没有开放价」，不是 `status == "wished"`

家长定价之后，那条单子**仍然停在 `wished`** —— 它要等孩子真的来兑换，
才会被复用途中并翻成 `committed`。

于是「还没被回应」和「已开放、等孩子来换」在**数据上是同一个状态**。

只按状态算的话，家长定完价、红顶栏的 👀 红点**永远消不掉**：
家长再点进去，看到的却是一件已经开放的商品 ——
**一个点不完的数字比没有红点更糟**。

判据取「这件商品现在有没有开放价」（`voucher_price > 0 AND closed_at = 0`）：
**定价就是家长的回应**。`closed_at > 0` 的行不算开放（家长把它关了），
那时重新变回「等你回应」是对的。

对应前端 `domain/wish.ts` 的 `wishesAwaitingReply`。

**实测**：

```
许愿后（未定价） → wished_count = 1
家长定价 20 券   → wished_count = 0   ← 红点会消
```

### 3.8 定价 = 上架，而且是**就地能换**

家长原话（2026-10-29，两轮 —— 第二轮回过头纠正了第一轮的做法）：

> 「爸爸妈妈已经定好价格的，相当于添加了兑换，应该出现在兑换列表里。」
>
> 「兑换 里的东西都是一样，都能用兑换券或者积分，包括游戏也一样。
>   不需要去心愿商城换。心愿商城只是标明心愿的。」

所以定价之后，那件商品出现在**孩子的「兑换」那一格**，但是：

- **不是单独一块**。没有「🛍️ 心愿商城 · 爸妈开放了」这个标题 ——
  它和家里的兑换品排在**同一个分类列表**里（分类固定 `gift`，
  只决定分组标题、**不决定付款规则**），按价格混排。
- **不是一道门**。点「换这个」就在这一行扣币、生成订单，
  不再跳去另一个收银台。

`POST /api/redeem/list` 返回的每一行都带 `source`：

| `source` | 来源 | 付款规则 |
|---|---|---|
| `redeem` | 家长自己加的兑换品（`redeem_item`） | 券 → 积分 |
| `wish` | 心愿商品被家长定了价（`wish_item` + `wish_offer`） | **同一个** `PlanRedeemPayment` |

**实测**（混排，按价格升序）：

```
[redeem] 🍪 一份小饼干      价格=10   付款=10 兑换券
[wish]   🦖 恐龙模型套装    价格=20   付款=10 兑换券 + 10 积分
```

#### `wishShelf` 的四个排除条件，一个都不能少

1. **没定价 / 已关闭** —— 那是「等爸妈回应」，不是能换的东西
2. **已下架**（`archived`）—— 目录里撤掉的商品不该还挂在兑换列表上
3. **已经拥有**（gamebox）—— 走 `ownedGameSet` 同一套规则。
   少了这一条，孩子会在这里看到自己早就换到的游戏
4. **盲盒池空** —— 池子空了还摆在「能换什么」里，点进去只会被拒

另外排除**已在走流程**的单子（`committed` / `confirmed`）：
那件东西已经付过钱了，再列一次等于鼓励孩子换第二遍。
`wished` **不排除** —— 家长定了价，孩子就该能去换。

### 3.9 兑换记录是**两张表合成的一条时间线**

家长报的 bug（2026-10-29）：

> 「孩子刚兑换了一个游戏，为啥我兑换记录里看不到。」

问题出在**两张表**：家里那几件写 `redeem_record`，心愿/游戏写 `wish_order`。
兑换记录页只读前者 ⇒ 孩子在兑换页换了一款游戏，扣了钱、游戏也装上了，
记录里却一个字都没有。

界面上看不出任何异常，只有家长去对账时才会发现
「**券少了 30，找不到花在哪**」。

所以 `POST /api/redeem/history` 读**两张表**、排一条时间线：

- 按 `created_at` 倒序
- 每行带 `source` / `pay`（「30 兑换券 + 20 积分」）/ `tag` / `pending` / `delivered`
- **`wished` 不算兑换** —— 那是「想要」，一分钱没扣。
  列进来的话会显示「🎫 0」或者按标价显示，两种都是**假账**

#### ★ 已交付的数字商品**不算**待兑现

它确实还停在 `committed`（等家长点「完成这一单」），但**东西孩子已经拿到手了**。

计数把它算进去的话，记录页会出现「**红点 1 + 绿标签「已放进游戏柜」**」
这种自相矛盾的一屏（前端截图走查抓到过）。

```go
pending := (status == committed || status == confirmed) && openedGameID == ""
```

家长那边的收尾提示在心愿页顶部，**不靠这个数**。

#### 付款文案：两屏必须同源

「我许的愿」和「兑换记录」对同一笔钱必须说**同一句话**，
都走 `entities.DescribeRedeemPayment`。

前端曾经自己拼过一版「🎫 20 张」，同一笔钱两屏两种说法 ——
家长对账时要先在脑子里翻译一次。

> 前端还有**两个语域**的区分（行内预览用图标 `🎫 250 + 🪙 10`，
> 句子/确认/回执用文字 `250 兑换券 + 10 积分`），
> 判据是「旁边有没有余额条」。
> 这是**渲染层**的事，服务端把结构化分账（`Plan`）和文字版都给出来，
> 客户端自己选。

**实测**：

```
[redeem] 🍪 一份小饼干   10 积分                [待兑现]      pending=true
[wish]   🎁 游戏盲盒     10 兑换券 + 20 积分    [等爸妈确认]  pending=false  ← 已交付
[wish]   🎁 游戏盲盒     10 兑换券 + 20 积分    [已取消]      pending=false
```

对应前端 `domain/redeemHistory.ts` 的 `redeemHistory()`。

### 3.10 隐私

- **外链 `buy_url` 只在家长端返回**（`as_parent: true`），孩子端读不到
- **收货信息在孩子端脱敏**：手机号 `****8000`、详细地址不回
- `purge_after` 字段：下单后 90 天自动抹除（预留）

> ⚠️ 当前 `as_parent` 是请求里的**显式标记**，不是真正的家长身份验证。
> 家长 PIN 还没实现 —— **上生产前必须接真正的家长校验**。

## 4. 游戏解锁与下载分发

### 4.1 为什么必须用 OSS/CDN

实测 `kid-quest-farm-2d/public/games/`：**1492 个文件 / 169 MB**
（21 款游戏，单包 3~6 MB，外加贴图资源）。

这个体量**不能走 API 进程**：

1. Go 的 HTTP 服务每连接占一个 goroutine + 缓冲，几十 MB 的传输会把
   连接数和内存打满，正常 API 请求被挤掉
2. 带宽成本落在应用实例上，扩容只能加实例，比 CDN 贵一个量级

**所以：包体放对象存储/CDN，客户端直连下载。**
服务端只负责三件事：

1. 发「目录」（`catalog.json` + Ed25519 签名）
2. 发下载地址
3. 记录版本与发布状态

### 4.2 客户端已有的校验链（不要重复发明）

前端 `src/games/install.ts` 已经定义了完整链路：

```
catalog.json ──┐
               ├─► 验签 ──► 解析 ──► 找到那一款 ──► 取包 ──► 验 SHA-256 ──► 代码文本
catalog.json.sig ┘
```

**公钥烧进 APK**（`catalogKey.ts`）。所以服务端只要产出符合该格式的
catalog + 签名即可。

### 4.3 catalog 格式（必须与前端一致）

```json
{
  "version": 1,
  "games": [
    {
      "id": "cloudfarm",
      "name": "云边小农场",
      "version": "1.1.5",
      "url": "cloudfarm/cloudfarm-1.1.5.plugin.mjs",
      "sha256": "…64位小写hex…",
      "size": 4388300,
      "assetBase": "cloudfarm/"
    }
  ]
}
```

签名契约（`pkg/ed25519sign`）：

| 项 | 值 |
|---|---|
| 算法 | Ed25519 |
| 公钥 | **原始 32 字节**（base64 存前端） |
| 私钥 | 64 字节（seed + public），base64 存配置 |
| 签名对象 | **catalog.json 的原始字节**（Ed25519 内部已做哈希，**不要**再套 SHA-256） |
| 签名格式 | **原始 64 字节**，`.sig` 文件里是**单行 base64**（前端用 `atob` 解，换行会解出垃圾） |

### 4.4 fail closed

**没配私钥 = 不能签 = 目录接口报错。**

不提供「没配就跳过签名」的分支 —— 那等于让
「谁拿下静态服务器，谁就能在孩子手机里跑任意代码」变成默认行为。
前端 `catalogKey.ts` 的空公钥是同一个态度。

### 4.5 接口

| 接口 | 鉴权 | 说明 |
|---|---|---|
| `GET /api/game/catalog` | **公开** | catalog.json 原始字节（客户端要对**这串字节**验签，不能重编码） |
| `GET /api/game/catalog.sig` | **公开** | 单行 base64 签名 |
| `POST /api/game/update-check` | 需登录 | 客户端上报已装版本，返回有更新的 |
| `POST /api/game/download` | 需登录 | 下载地址（**校验是否已拥有**） |
| `POST /api/admin/game/release/publish` | 后台令牌 | 发布版本 |
| `POST /api/admin/game/release/list` | 后台令牌 | 版本列表 |
| `POST /api/admin/game/release/self-check` | 后台令牌 | 自检密钥，返回公钥 |

> 目录为什么公开：客户端在**装包前**就要拿到目录，
> 而且目录地址是**烧进 APK** 的，不存在「先登录再拉目录」的时机。
>
> 安全靠两件事，不是靠鉴权：
> 1. Ed25519 签名 —— 中间人改不了目录内容
> 2. 客户端验包 SHA-256 —— 包体被换会被发现

### 4.6 发布版本

`POST /api/admin/game/release/publish`（`X-Api-Token`）

```json
{
  "game_id": "cloudfarm",
  "version": "1.1.5",
  "channel": "stable",
  "url": "cloudfarm/cloudfarm-1.1.5.plugin.mjs",
  "sha256": "……64位小写hex……",
  "size": 4388300,
  "min_host_api": 1,
  "release_notes": "修了几个 bug"
}
```

校验：

| 项 | 规则 |
|---|---|
| `sha256` | 必须 64 位小写 hex（**不做补零/截断这类宽容匹配**） |
| `asset_base` | 必须以 `/` 结尾（否则客户端拼资源路径会少一个斜杠） |
| `size` | 不超过 `MaxPackageBytes`（默认 64MB） |

**事务边界**：把同 `game_id + channel` 的旧版本置为非 active +
插入新版本，**必须原子** —— 拆开会出现「两个 active」或者
「一个 active 都没有」的瞬间。

### 4.7 请求处理流程

```
① 客户端启动 → GET /api/game/catalog + /api/game/catalog.sig
                （验签 → 解析 → 知道自己能装什么）

② 用户点「安装 / 更新」→ POST /api/game/download { game_id }
                （服务端校验是否已拥有 → 返回 URL + sha256）

③ 客户端从 OSS/CDN 直连下载 → 验 SHA-256 → 装入

④ （可选）POST /api/game/update-check
                （上报已装版本 → 服务端比对 → 返回更新列表）
```

### 4.8 实测验证

签名链（用客户端的方式验签）：

```
VERIFY OK
TAMPER DETECTED (expected)
```

更新检查：

```
已装 1.1.4，服务端 1.1.5 → updates=1  ✓
已装 1.1.5              → updates=0  ✓
```

下载权限：

```
cloudfarm（默认拥有）→ 200 + 下载信息  ✓
prizepark（未拥有）  → 10040401        ✓
```

## 5. 数据模型

| 表 | 说明 |
|---|---|
| `redeem_item` | 兑换商品（家长创建） |
| `redeem_record` | 兑换记录（含 `coupon_paid` / `points_paid` 分账 + 余额快照） |
| `wish_item` | 心愿商品目录（种子同步自前端常量；运营可改） |
| `wish_offer` | 家长对本商品的开放设置（`uid + item_id`） |
| `wish_order` | 心愿单（含商品快照 + `vouchers_held` + `opened_game_id`） |
| `wish_code` | 兑换码（**存 sha256，不存明文**） |
| `game_release` | 游戏版本发布（`game_id + channel + version`） |

### 5.1 商品目录为什么入库（而前端是常量）

前端把目录做成 TS 常量（`games/wishCatalog.ts`），理由是
「改一个商品文案不该触发 Dexie 迁移」。

服务端没有这个约束，而且**运营需要能上架/改价/下架** —— 所以入库，
但**种子数据**从前端同步（`seed/wish_catalog.go`），保持两边口径一致。

游戏盒子和盲盒池**从 `game` 表推导**，不手写 ——
21 款游戏各写一条的话，下次加游戏就一定会漏，
而漏掉的那款在界面上表现为「盒子里没有它」，**不报错**。

## 7. 已知问题与修复记录

### 7.1 SQLite 索引名全局唯一，导致 auto-migrate 失败（已修复）

**现象**：服务启动即 panic —— `index uk_uid_item already exists`。

**原因**：`RedeemItem` 和 `WishOffer` 都用了 `uniqueIndex:uk_uid_item`。

SQLite 的索引名是**整个数据库共享**的（MySQL 是每表独立命名空间）。
所以这个错**只在开发环境（SQLite）暴露**，上生产（MySQL）反而看不出来 ——
反过来说，开发环境能跑不代表生产能跑，这次是反过来。

**修复**：索引名加表前缀（`uk_redeem_uid_item` / `uk_wish_offer_uid_item`）。

**教训**：新增表时索引名一律带表名前缀，别用 `uk_uid_xxx` 这种通用名。

### 7.2 事务内用外层 DB 句柄导致死锁（已修复）

`WalletService.GetWalletWithTx` 的存在就是这个原因 ——
详见 [`SAVE_SNAPSHOT.md`](./SAVE_SNAPSHOT.md) §8.1。

`Redeem` 和 `Wish.Redeem` 里所有事务内调用都走 `WithTx` 版本。

### 7.3 幂等键退化成一个常量，导致**再也换不了**（已修复）

**现象**：取消心愿后再想兑换同一件商品，报 `10020801 该笔记录已存在`。
换个商品能换，但**同一件永远换不了**。

**原因**：账本幂等键写的是

```go
IdempotencyKey: "wish_redeem:" + req.ClientRequestID
```

而 `ClientRequestID` 是**可选**的。客户端不传时（本项目前端就不传），
这个键退化成常量 `"wish_redeem:"` —— 第二次兑换必然撞账本唯一索引。

**修复**：订单号在**扣款之前**定下来，幂等键用订单号：

```go
IdempotencyKey: "wish_redeem:" + order.OrderID        // 券
IdempotencyKey: "wish_redeem_points:" + order.OrderID // 积分
```

「客户端重试」的幂等由**状态 CAS** 兜着（重试时订单已是 `committed`，
`UpdateOrderCAS(from=wished)` 会失败），不需要靠账本键。

**教训**：幂等键里**不能出现可选字段**。要么保证非空，要么用必有的业务主键。
这个 bug 的隐蔽之处在于「第一次能用、第二次才炸」——
测试如果只跑一遍兑换路径就发现不了。

**测试防线**：E2E 里必须包含「取消 → 重新兑换同一件商品」这一步。

## 8. 部署清单

### 8.1 生成密钥对

```bash
# 任意 ed25519 工具，或：
go run ./cmd/seed keygen
```

输出：

```
私钥（base64）→ 环境变量 TF_GAME_CATALOG_KEY，**绝不提交进仓库**
公钥（base64）→ 粘到前端 src/games/catalogKey.ts 的 CATALOG_PUBLIC_KEY_B64，并提交
```

### 8.2 上传游戏包到 OSS

`public/games/` 下 21 款，共 169 MB。上传后拿到公网地址。

### 8.3 配置

```yaml
GameDistribution:
  CatalogPrivateKey: ''          # 走环境变量
  CatalogBaseURL: 'https://cdn.example.com/games'   # 可选
  PackageBaseURL: 'https://oss.example.com/games'   # 包下载根
  CatalogCacheSeconds: 300
  SignedURLTTLSeconds: 0         # 0 = 公开 CDN 地址
```

### 8.4 发布版本

对每款游戏调一次 `publish`，填 OSS 地址 + 算好的 SHA-256 + 体积。

### 8.5 验证

```bash
curl http://<host>/api/admin/game/release/self-check -H "X-Api-Token: <token>"
# 返回的 public_key_base64 必须和前端 catalogKey.ts 里的一致
```

**这一步不能省** —— 换密钥后如果两边不一致，症状是
「所有游戏都装不上」，而排查的人会先去怀疑网络。
